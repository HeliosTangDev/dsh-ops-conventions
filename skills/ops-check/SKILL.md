# ops-check — 自检与审核清单

## 默认规则

**做任务默认带自检/复核环节**，除非确定不会出错。

## 改完立刻验证（按对象选一种）

| 对象 | 最小验证 |
|---|---|
| 脚本 | 能加 `-Once`/`-DryRun` 的先冒烟；语法用 Parser 检查；改完真跑一次 |
| 看板/UI | 连续跑几秒看是否报错、stderr 是否为空 |
| 配置 | 改后重启/重载并读回生效值 |
| 数据结构/批量 | 抽样读回，不只看退出码 |
| 文档/索引 | 抽查链接是否存在、表里是否漏行 |

## 批量任务

- 跑完**自动执行外部校验**（`taskrun -VerifyCommand`），不是只看"跑完了"。
- 失败项要**看原因**再决定忽略还是修（别只数个数）。
- 验证要"读回"：状态文件、行数、去重数、目标文件是否真的变对。

## 失败与回滚

- 还原后 `Get-FileHash` 与备份逐字节比对一致，才删备份。
- 把自己新增的残留文件、测试目录一并清掉，只留原状。

## 结论口径

- **带证据**：命令 + 实际输出（或数值），不要"应该没问题"。
- 记忆与实测冲突时**以实测为准**，并回写纠正记忆。
- 报"修好了"之前必须有一次成功的实测输出。

## 优化与投入（效率）

- 提出「继续优化」之前，先给**收益 vs 成本**判断（时间、token、维护面）。
- 收益低于成本时**直接建议停止**，并说明依据；由汤海峰做最终决定。
- 不把「可以一直优化」当成无限投入的理由。

## 事实与推断（硬性）

1. **事实必须取证后再写**：插件状态、会话 id、版本号、文件内容这类可查项，先查再写；查不到就写「查不到」，不写成结论。
2. **推断必须显式标注**：写成「推断：…」，并给出依据；不把推断混进事实陈述。
3. **操作顺序：先复制成功再删旧**，绝不「先删后复制」；删除前确认源与目标路径（见 ops-files）。
