# ops-dsh — DSH / 插件 / 升级清单

## 插件

1. 找插件**只用 `dshm_search`**（不用 web_search/bash）；按用户给的关键词检索，一次一条消息。
2. 安装/升级/卸载：**用户点名或确认后**才做；装完需要重启，主动说明并提供重启。
3. 桌面端能力受限：只读市场 + 安装新包 + 开关；升级/卸载/自启/重启会被结构化拒绝 → **如实转述，不要重试**。
4. 开关（toggle）在用户同一句已明确表达时可直接执行，并说明「即时生效 / 需重启」。

## 升级 DSH 宿主

1. **顺序**：先等插件作者适配（看有没有插件更新）→ 再升宿主。
2. **兼容判定要用机器**：`node dsh_upgrade_check.js <目标版本>`；**不要手工推断 semver**——预发布版本不会被普通区间匹配（`satisfies` 为 false 但实际可用），声明是背书不是测试。
3. 升级前：备份 profile（`_backups\`）+ 采集基线（`dsh_capture_baseline.ps1`）。
4. 升级后：`node dsh_verify.js <版本>` 验证；失败用 `dsh_rollback.ps1 -BackupDir <备份>`。
5. **不自主升级**，需要用户拍板。

## 记忆系统问题的三层归因（硬性）

遇到「约定没生效 / 该记住的没记住 / 该做的没做」，**三层都要查**，不许只查一层就下结论：

| 层 | 查什么 | 证据 |
|---|---|---|
| 插件层 | 是否加载、是否注入、注入内容对不对 | `~\.dsh\ops-conventions\ops-conventions.log`（`plugin loaded` / `inject vN session=…`）；`_tools\skills\VERSION` 是否已改 |
| Viking 层 | 记忆是否写入、能否检索到、注入是否到达上下文 | `openviking find` 实际检索结果；会话里有无记忆块 |
| 模型层 | 看到后有没有执行、判断标准是否明确 | 回复是否按清单做了、有没有把推断当事实、该直接做的有没有拿去问 |

- 三层都过一遍再归因；只查一层就归因 = 判定错误。
- 优化也要三层联动：插件改触发/措辞 → 约定改标准 → 记忆记判据。

## 其他

- 不要手改 `.agent-teams` 等运行时状态文件；不要读插件源码去"修"计划。
- 启动链/端口/profile 配置排查：先看日志与进程，再动手；改配置前备份。
- 结论写进 `TOOLS.md` 或记忆（含日期与证据）。
